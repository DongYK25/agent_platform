# fastapi-scaff 工程导读

这份说明按你已经用过的 Django、Flask 来对照当前工程。项目由 [fastapi-scaff](https://github.com) 生成，架构叫 **ASM**：

- **A**pi：接收 HTTP 请求、校验参数、返回响应
- **S**ervices：业务逻辑
- **M**odels：数据库表，以及请求/响应的数据结构

一次请求的方向是：

```text
runserver.py
  -> app/main.py          创建 FastAPI 应用
  -> app/core             中间件、异常、配置、数据库、日志
  -> app/api              路由（相当于 views / blueprint）
  -> app/services         业务
  -> app/models           表和数据结构
```

和你熟悉的框架放在一起看：

| 这件事 | 本工程 | Django | Flask |
| --- | --- | --- | --- |
| 启动 | `runserver.py` | `manage.py runserver` | `flask run` / `app.run()` |
| 应用对象 | `app/main.py` 里的 `app` | `wsgi.py` 里的 `application` | `app = Flask(__name__)` |
| 配置 | `config/app_*.yaml` + `.env` | `settings.py` | `app.config` / `config.py` |
| 路由 | `app/api/**` 自动注册 | `urls.py` | `@app.route` / Blueprint |
| 视图 | 路由函数，很薄 | `views.py` | 视图函数 |
| 业务 | `app/services` | 常写在 view 里，或单独的 services | 常写在视图函数里 |
| 表 | SQLAlchemy 模型 | `models.Model` | `db.Model`（Flask-SQLAlchemy） |
| 入参校验 | Pydantic 模型 | Form / DRF Serializer | Flask 里常手写，或用 Marshmallow |
| 中间件 | `app/core/middleware.py` | `MIDDLEWARE` | `before_request` / `after_request` |
| 统一响应 | `Responses.success/failure` | `JsonResponse` | `jsonify` |
| 当前用户 | `Depends(get_current_user)` | `request.user` | `current_user`（Flask-Login） |
| 全局对象 | `g`（进程级单例） | `django.conf.settings` | `current_app`。注意：不是 Flask 的请求级 `g` |

下面按目录讲每个文件在做什么。

---

## 1. 根目录

```text
agent_demo/
├── app/                  应用代码（对应 Django 项目包，或 Flask 的 app 包）
├── config/               配置（对应 settings）
├── docs/                 文档，本文件就在这里
├── tests/                测试，目前是空的
├── runserver.py          启动脚本
├── requirements.txt      依赖
├── pyproject.toml        Ruff / BasedPyright 的检查配置，不是运行配置
├── uv.lock               uv 锁定的依赖版本
├── .python-version       Python 3.12
├── .gitignore
├── LICENSE
└── README.md             脚手架自带说明
```

脚手架还能加上 Celery、Docker、Alembic 迁移。当前这次生成没有带这些目录，所以工程里看不到 `app_celery/`、`Dockerfile`、`runmigration.py`。需要时再用 `fastapi-scaff tpl` 加。

### `runserver.py`

开发时的启动入口，对应：

- Django：`python manage.py runserver`
- Flask：`flask run`，生产环境再换成 gunicorn

它做两件事：

1. 解析 `--host`、`--port`、`--workers`、`--log-level`、`--reload`、`--gunicorn`。
2. 默认用 **uvicorn** 跑 `app.main:app`。非 Windows 且加了 `--gunicorn` 时，改用 gunicorn，worker 类型仍是 `uvicorn.workers.UvicornWorker`（gunicorn 管进程，uvicorn 跑异步）。

文件底部的默认值是：`0.0.0.0:8000`，1 个进程，`reload=False`。本地改代码想自动重启，启动时加上 `--reload`。

Windows 上 gunicorn 不可用，所以现在走的是 uvicorn 分支。

### `requirements.txt`

运行依赖。和 Django 的 `requirements.txt` 一样，只是列出的库不同：

| 包 | 作用 | 你可能用过的对应物 |
| --- | --- | --- |
| `fastapi` | Web 框架 | Django / Flask 本身 |
| `uvicorn` | ASGI 服务器 | `runserver`、gunicorn、waitress |
| `SQLAlchemy` + `aiosqlite` | ORM，异步 SQLite | Django ORM、Flask-SQLAlchemy |
| `PyJWT` + `bcrypt` | 令牌和密码哈希 | `django.contrib.auth`、Flask-JWT-Extended |
| `python-dotenv` + `PyYAML` | 读 `.env` 和 yaml | django-environ、Flask 的 `config.from_pyfile` |
| `toollib` | 脚手架作者的工具库：配置模型、日志、SQL CRUD 助手 | 没有直接对应，当第三方工具用 |
| `fastapi-scaff` | 生成工程、以后 `add` 新接口用的命令行 | `django-admin startproject` |

`pyproject.toml` 只配了代码检查（Ruff 相当于 flake8 + isort，BasedPyright 相当于 mypy），不影响启动。

## 2. `app/`：应用本体

### `app/__init__.py`

只定义了 `APP_DIR`，也就是 `app/` 的绝对路径。后面拼配置目录、模型目录、数据库文件路径都从这里出发。Django 里你很少自己写这个，因为 `BASE_DIR` 放在 `settings.py`。

### `app/main.py`

整个应用的组装点，接近这三样东西合在一起：

- Django 的 `wsgi.py` / `asgi.py`（交出 `application`）
- Django 的根 `urls.py`（把路由挂上去）
- Flask 的 `create_app()`

它做的事按顺序是：

1. `g.setup()`：把配置、日志、数据库会话准备好。类似 Django 启动时加载 `settings`，或 Flask 工厂函数里 `db.init_app(app)`。
2. 按配置决定要不要打开 `/docs`、`/redoc`、`/openapi.json`。生产配置里 `APP_DISABLE_DOCS: true`，这三个地址就会关掉。FastAPI 自带的交互文档，Django 要装 drf-spectacular 一类的包才有，Flask 通常没有。
3. `lifespan`：进程启动和退出时打日志。对应 Django `AppConfig.ready()`，或 Flask 里你自己写的启动钩子。
4. `middleware.add_middleware_and_exceptions(app)`：挂中间件和异常处理。
5. `api.register_routers(app)`：扫描 `app/api`，把路由注册进来。你不用在这里手写 `include_router`。

## 3. `app/api/`：接口层

这一层只处理 HTTP：路径、参数、权限、调用 service、包装响应。业务计算不要堆在这里。

Django 对照：`views.py` + `urls.py`。
Flask 对照：Blueprint 里的视图函数。

### `app/api/__init__.py`：自动注册路由

`register_routers()` 会递归扫描 `app/api`，规则是：

- 跳过 `__` 开头的文件和目录。
- 目录可以定义 `_prefix`，会拼进 URL。
- 只收集名字是 `router` 或 `xxx_router`、并且值是 `APIRouter` 的对象。
- 模块里 `_active = False` 时，整个文件不注册（想临时下线一个接口模块，改这个开关即可）。
- 扫描深度默认 1 到 2。所以 `app/api/v1/user.py` 会被收录，再往下套一层目录就不会。

这相当于 Django 自动发现每个 app 的 `urls.py` 再 `include`，或 Flask 启动时自动 `register_blueprint`。你新增 `app/api/v1/order.py` 并写出 `router = APIRouter()`，重启后就会挂上，不必改 `main.py`。

### `app/api/v1/__init__.py`

```python
_prefix = "/api/v1"
```

这个目录下所有接口的 URL 都会带 `/api/v1`。等于：

```python
# Django
path("api/v1/", include("app.api.v1.urls"))

# Flask
app.register_blueprint(bp, url_prefix="/api/v1")
```

以后要做 v2，再建 `app/api/v2/`，写上 `_prefix = "/api/v2"`。

### `app/api/default/__init__.py` 和 `health.py`

`_prefix = ""`，所以健康检查在根路径：`GET /health`。

它不走 `Responses` 那套业务包装，直接返回 `status`、`version`、`timestamp`。这是给负载均衡、K8s、监控探活用的，Django 里你也会单独写一个不套业务格式的 health 视图。

### `app/api/v1/user.py`

用户模块的示例接口，也是你以后抄的模板。文件头三个约定：

| 变量 | 作用 |
| --- | --- |
| `_active = True` | `False` 则整个模块不注册 |
| `_tag = "user"` | OpenAPI 分组名。路由自己已经写了 `tags` 时，以路由上的为准 |
| `router` / `auth_router` | 两个 `APIRouter`，都会被自动挂上 |

现有接口：

| 方法 | 路径 | 谁能调 | 做什么 |
| --- | --- | --- | --- |
| GET | `/api/v1/users` | 登录且 `role == admin` | 分页列表 |
| POST | `/api/v1/users` | 不需要登录 | 注册 |
| GET | `/api/v1/users/{user_id}` | 已登录 | 查一个用户 |
| PUT | `/api/v1/users/{user_id}` | 已登录 | 改昵称、年龄、性别 |
| DELETE | `/api/v1/users/{user_id}` | 管理员 | 删除 |
| POST | `/api/v1/users/auth/login` | 不需要登录 | 登录，access token 放 JSON，refresh token 写 Cookie |
| POST | `/api/v1/users/auth/logout` | 已登录 | 登出，并清掉 Cookie |
| POST | `/api/v1/users/auth/refresh` | Cookie 里的 refresh token | 换一对新 token |

一个视图函数的形状，和 DRF 的 action、Flask 的视图一样薄：

```python
async def create_user(
    req: UserCreate,                              # 请求体，Pydantic 自动校验
    user_svc: UserSvc = Depends(get_user_svc),    # 注入业务对象
):
    data = await user_svc.create_user(req)
    return Responses.success(data=data)
```

对照：

- `req: UserCreate` ≈ DRF 的 `serializer.is_valid()`，或 Flask 里你自己 `request.get_json()` 再校验。校验失败不会进函数，框架直接返回 422，再被下面的异常处理收成统一 JSON。
- `Depends(...)` ≈ Django 在视图参数里拿到 `request.user`，或 Flask 用装饰器把当前用户塞进来。FastAPI 用依赖注入，而不是全局取。
- `responses=response_docs(...)` 只影响 `/docs` 里的示例，不改变真实返回值。类似给 drf-spectacular 补 schema example。

`auth_router` 和 `router` 分成两个，是为了在文档里分成 `user-auth` 和 `user` 两组。URL 前缀仍然都是 `/api/v1`。

### `app/api/deps.py`

认证依赖。Django 里这块散落在 `AuthenticationMiddleware`、`permission_classes`、`authentication_classes`。Flask 里是 `@login_required` 和 `current_user`。

这里提供三个依赖，视图函数按需 `Depends`：

| 函数 | 从哪读凭证 | 用途 |
| --- | --- | --- |
| `get_current_user` | 请求头 `Authorization: Bearer <access_token>` | 普通登录接口 |
| `get_current_user_from_refresh` | Cookie `x_refresh_token` | 刷新令牌 |
| `get_current_api_key` | 请求头 `X-API-Key` | 服务间调用。示例用户接口没有用它 |

校验步骤和 Django SimpleJWT、Flask-JWT-Extended 类似：解开 token，核对类型（access / refresh），再用用户自己的 `jwt_key` 验签。密钥优先用配置里的 `JWT_KEY`；没配则去 `users.jwt_key` 查。登出和刷新都会换一把新的 `jwt_key`，旧 token 随即失效，这是一种“服务端可作废”的做法，单纯的 JWT 本身是无状态、不能单独作废的。

`JWTUser` 是从 token 里还原出来的当前用户，字段有 `id`、`phone`、`status`、`role`、`nickname`、`avatar`。把它当成 `request.user` 用即可，它不是数据库模型。

## 4. `app/services/`：业务层

### `app/services/__init__.py`

空文件，只标明这个包是业务逻辑。

### `app/services/user.py`

用户相关的增删改查和登录。Django 项目如果写得比较整齐，这些会放在 `services.py` 或 model 的 manager 里；写得随便时，会直接堆在 `views.py`。Flask 小项目通常就写在视图函数里。这个模板强制拆开，是为了接口层可以换（HTTP、以后的 Celery 任务）而业务不用重写。

`UserSvc` 的方法都是 `async`，因为数据库会话是异步的。每个方法自己 `async with g.db_async_session()` 开一次会话，用完提交。这和 Django 每个请求自动包一层事务不同：这里要自己 `commit()`。不 commit 的写操作不会落库。

登录相关的时间：

- access token：2 小时，放在响应 JSON 里，前端之后放到 `Authorization` 头。
- refresh token：30 天，由接口层写入 HttpOnly Cookie，不出现在 JSON 的 `data` 里（`user.py` 路由里 `data.pop("refresh_token")`）。

`get_user_svc()` 用 `lru_cache` 做成单例，通过 `Depends` 注进视图。类本身没有请求状态，所以可以全局复用。不要把“当前请求的用户”存在 `UserSvc` 实例上。

## 5. `app/models/`：数据层

Django 习惯把“表”和“接口入参”分成 `models.py` 和 `serializers.py`。这个模板把两样都放在 `app/models/user.py`，读的时候要分开看。

### `app/models/__init__.py`

```python
class DeclBase(DeclarativeBase, CRUDMixin):
    """数据模型基类，集成 CRUD 操作"""
```

`DeclBase` ≈ Django 的 `models.Model`，或 Flask-SQLAlchemy 的 `db.Model`。

`CRUDMixin` 来自 `toollib`，所以 service 里能直接写 `User.fetch_all`、`User.create`、`User.update`、`User.delete`、`User.count`，不用每次手写 `select()`。把它理解成一个写好的 Manager / QuerySet 快捷方式。

### `app/models/user.py` 的两半

**表：`class User(DeclBase)`**

表名 `users`。字段包括手机号、邮箱、密码密文、jwt 密钥、状态、角色、昵称、头像、年龄、性别、最后登录时间、创建/更新时间。主键默认是去掉横线的 UUID。时间戳是整数（毫秒或秒由 `now_timestamp` 决定），不是 Django 常见的 `DateTimeField`。

启动时 `_db.py` 会 `create_all`：表不存在就建，不会改已有表的字段。这接近 SQLite 开发时的 `migrate` 的“建表”那一下，但没有版本化迁移。改字段后需要自己处理，或以后用脚手架的 `--migration`（Alembic，相当于 Django migrations）。

**入参：几个 Pydantic `BaseModel`**

| 类 | 用在哪 | Django / Flask 对照 |
| --- | --- | --- |
| `UserList` | 列表的 query：`page`、`size`、`phone`、`nickname` | DRF 的查询 Serializer，或 Flask 的 `request.args` |
| `UserCreate` | 注册 body，含密码强度、手机号、昵称校验 | `ModelForm` / DRF `CreateSerializer` |
| `UserUpdate` | 更新 body，字段都可选 | `PartialUpdateSerializer` |
| `UserLogin` | 登录 body：手机号 + 密码 | 登录表单 |

校验写在 `Field(...)` 和 `@field_validator` 上。不合法时 FastAPI 抛 `RequestValidationError`，中间件把它收成统一的 422 响应。你不用在视图里写 `if not phone`。

## 6. `app/core/`：基础设施

Django 里这些分散在 `settings`、`MIDDLEWARE`、日志配置、数据库配置。Flask 里分散在扩展初始化和 `errorhandler`。这里收成一个包。

### `app/core/__init__.py`：全局对象 `g`

`g` 是单例，第一次访问时才初始化：

| 属性 | 内容 |
| --- | --- |
| `g.config` | 配置 |
| `g.logger` | 日志 |
| `g.db_async_session` | 异步会话工厂，调用它得到一次数据库会话 |

**不要把它当成 Flask 的 `g`。** Flask 的 `g` 只活在一次请求里。这里的 `g` 活在整个进程里，用来放配置、日志、连接池。和一次请求有关的数据走 `context.py` 的 `ContextVar`，或走 `Depends`。

### `app/core/_conf.py`

配置加载顺序可以记成：代码里的默认值 < yaml < 环境变量。

1. `APP_ENV` 不是 `prod` 时，读取 `config/.env`。
2. 按环境选文件：`config/app_dev.yaml`、`app_test.yaml`、`app_prod.yaml`。没设 `APP_ENV` 时用 `dev`。
3. `Config` 是 `toollib` 的 `ConfModel`。同名环境变量可以覆盖 yaml。

换环境就是启动前设置 `APP_ENV=prod`，相当于 Django 的 `DJANGO_SETTINGS_MODULE=proj.settings.prod`，或 Flask 的 `FLASK_ENV` / `APP_CONFIG`。

`DB_DRIVERNAME` 这些字段在类上没有默认值，yaml 里必须有，否则启动失败。当前三个环境都是 SQLite，文件分别在 `data/db/app_dev.sqlite3`、`app_test.sqlite3`、`app_prod.sqlite3`。

### `app/core/_db.py`

建数据库引擎和会话，并在启动时扫 `app/models`、对继承了 `DeclBase` 的类执行 `create_all`。

异步驱动是 `sqlite+aiosqlite`（配置项 `DB_ASYNC_DRIVERNAME`），业务代码用这个。建表用同步驱动 `sqlite`（`DB_DRIVERNAME`），因为 `create_all` 走同步引擎。换 MySQL / PostgreSQL 时，两行驱动名、账号、主机一起改，业务代码不用改。

SQLite 文件路径是相对项目根目录的，父目录不存在会自动创建。

### `app/core/_log.py` 和 `context.py`

`context.py` 只有一个 `ContextVar`：`request_id`。每个请求一个 ID，异步任务之间不会串。这是线程本地 / Flask `g.request_id` 在 async 里的写法。

`_log.py` 用 `toollib`（底层是 loguru）初始化日志，并把 `request_id` 带进每条日志。是否打到控制台、是否写文件、目录、级别，都来自 yaml 的 `APP_LOG_*`。`APP_DEBUG=true` 时级别是 DEBUG，否则 INFO。日志目录默认 `logs/`，已被 `.gitignore` 忽略。

### `app/core/status.py`

业务状态码，不是 HTTP 状态码的简单别名。每一项是三元组：`(业务码, 文案, HTTP 状态码)`。

| 种类 | 例子 | 含义 |
| --- | --- | --- |
| 成功 | `SUCCESS = (0, "操作成功", 200)` | HTTP 200，业务码 0 |
| 失败 | `FAILURE = (1, "操作失败", 400)` | 未归类的失败 |
| HTTP 对应 | 400 / 401 / 403 / 404 / 422 / 500 | 和 HTTP 状态对齐 |
| 通用业务 | `10000` 记录不存在，`10001` 记录已存在 | 给前端分支用 |
| 用户业务 | `10101` 账密错误，`10102` 用户禁用，`10103` 权限不足 | 用户模块专用 |

新增一种业务错误时，在这里加一项，然后 `raise CustomException(status=Status.XXX)`。前端看 JSON 里的 `code`，不要只看 HTTP 状态。Django 项目里你可能用过一组常量，或 DRF 的自定义 exception；这里就是那个常量文件。

### `app/core/exceptions.py`

`CustomException` 带着 `Status`。在 service 里抛出它，视图不用 try/except，异常处理会接住并转成 JSON。

```python
raise CustomException(status=Status.RECORD_NOT_EXIST_ERROR)
```

≈ Django REST framework 的 `raise NotFound()` / `APIException`，或 Flask 的 `abort(404)`。区别是这里的响应体格式由 `Responses.failure` 统一决定。

### `app/core/middleware.py`

`add_middleware_and_exceptions()` 注册两类东西。

**中间件**

- `HttpMiddleware`：每个请求生成或沿用请求头 `X-Request-ID`，放进 `request_id_var` 和 `request.state.request_id`，响应头再带回去。未捕获的异常在这里记日志并返回 500。类似 Django 的一个自定义 middleware，或 Flask 的 `before_request` + `teardown_request`。
- `CorsMiddleware`：跨域，读取 yaml 里的 `APP_ALLOW_ORIGINS` 等。对应 `django-cors-headers`、`flask-cors`。当前配置是 `*`，上线前要收成真实前端域名；`allow_credentials` 为 true 时，浏览器并不接受 `*` 配凭证，这一点和 Django 里一样。

**异常处理**（对应 Flask `@app.errorhandler`，或 Django 的自定义 `handler500`）

| 捕获 | 变成 |
| --- | --- |
| `CustomException` | `Responses.failure`，用异常里的业务码 |
| `RequestValidationError` | 422，文案取第一条字段错误 |
| `HTTPException` | 按 HTTP 状态码映射到 `Status` |

三种处理都会打日志，并带上 query 和 body，方便对照 `request_id` 查问题。

### `app/core/responses.py`

所有业务接口的 JSON 外形：

成功：

```json
{
  "msg": "操作成功",
  "code": 0,
  "data": {},
  "request_id": "..."
}
```

失败（多一个 `error` 字段，因为文件里 `_EXPOSE_ERROR = True`）：

```json
{
  "msg": "记录不存在",
  "code": 10000,
  "data": null,
  "error": "...",
  "request_id": "..."
}
```

Django 的 `JsonResponse`、Flask 的 `jsonify` 不会强制这层外壳，这是项目自己的约定。前端应统一读 `code` 和 `data`。

`Responses.stream` 用于流式输出，当前示例接口没有用到。

`response_docs()` 只生成 OpenAPI 示例。参数是字段名到类型的描述，例如 `"id": "str"`，文档页会把它渲染成示例，不会做运行时校验。

## 7. `app/utils/`：工具

和业务无关、可复用的函数。Django 里常叫 `utils.py`，Flask 项目也一样。

| 文件 | 作用 | 对照 |
| --- | --- | --- |
| `jwt_util.py` | 签发 / 校验 JWT，bcrypt 哈希和校验密码，生成 `jwt_key` | `django.contrib.auth` 的 `make_password` / `check_password`，加上 SimpleJWT |
| `cookie_util.py` | 把 refresh token 写成 Cookie `x_refresh_token`，路径 `/api`，`httponly`，`samesite=lax`。`APP_ENV == prod` 时 `secure=True` | Django `response.set_cookie`，Flask `resp.set_cookie` |
| `api_key_util.py` | 生成 API Key 的小工具，可单独运行。校验在 `deps.py`，合法 key 列表来自配置 `API_KEYS` | DRF 的 API key 方案 |
| `ext_util.py` | `gen_uuid_hex()`、`now_timestamp()`，给模型默认值用 | Django 的 `uuid4`、`auto_now_add` |

`jwt_util.py` 底部有 `if __name__ == "__main__"`，可以直接 `python -m app.utils.jwt_util` 打一个示例 token，方便本地调试。里面的示例密钥只用于这个脚本，不要当成生产密钥。

## 9. 走一遍登录，把层次串起来

`POST /api/v1/users/auth/login`，body 是 `{"phone": "...", "password": "..."}`。

1. uvicorn 收到请求，进入 `app`。
2. `CorsMiddleware`、`HttpMiddleware` 先跑。后者写入 `X-Request-ID`。
3. 自动注册的路由匹配到 `auth_login`。Pydantic 用 `UserLogin` 校验 body，不通过则变成 422。
4. `Depends(get_user_svc)` 给出 `UserSvc`。这个接口没有 `get_current_user`，所以不要求登录。
5. `UserSvc.auth_login` 按手机号查 `users`，核对状态和 bcrypt 密码，签发 access / refresh token，更新 `jwt_key` 和 `last_login_at`，`commit`。
6. 视图从返回值里取出 refresh token，`set_refresh_token_cookie` 写到响应，JSON 里只留 access token 和 `user_info`。
7. 响应体是 `Responses.success` 的那四字段。响应头带 `X-Request-ID`。

列表、删除接口多一步：`Depends(get_current_user)` 先验 access token，再在视图里看 `current_user.role` 是不是 `admin`。权限判断目前写在视图里，没有单独的 permission 类。Django 的 `permission_classes` 如果要复用，可以再抽一个 `Depends`。

## 10. 加一个新模块时改哪里

以“订单”为例，和 Django 里新建一个 app 是同一类工作：模型、业务、路由三处，外加需要的错误码。

1. `app/models/order.py`：`class Order(DeclBase)` 定义表；再写 `OrderCreate` 这类 Pydantic 模型定义入参。重启时 `create_all` 会建新表（已有表的字段变更不会自动迁移）。
2. `app/services/order.py`：`OrderSvc`，数据库操作放这里，错误用 `CustomException`。
3. `app/api/v1/order.py`：`router = APIRouter()`，路径写成 `/orders`。需要登录就加上 `Depends(get_current_user)`。返回用 `Responses.success`。
4. 新的业务错误加到 `app/core/status.py`。
5. 不用改 `main.py`。`_prefix` 已经在 `app/api/v1/__init__.py`，最终路径是 `/api/v1/orders`。

也可以在项目根目录执行脚手架命令 `fastapi-scaff add <name>`，它会按同样的分层帮你生成文件，生成后再按业务改。

约定再记三条：

- 路由变量名必须是 `router` 或 `xxx_router`。
- 模块不想上线时设 `_active = False`。
- 精确路径和带路径参数的路由，精确的写在前面。文件里已有注释提醒这一点；同一 `APIRouter` 上 `/users/auth/login` 应排在 `/users/{user_id}` 之前，避免被当成 `user_id`。

## 11. 和 Django、Flask 最容易混的几点

1. **异步。** 视图和 service 是 `async def`，数据库用 `await`。不要在里面写普通的阻塞 `requests.get` 或同步的大循环占着事件循环。Django 默认视图是同步的，Flask 也是。
2. **`g` 是进程级的。** 配置、日志、会话工厂放这里。当前用户放 `Depends` 的参数里。
3. **要自己 commit。** `User.create` / `update` / `delete` 之后有 `await session.commit()`。读操作不用 commit。
4. **Pydantic 模型不是表。** `UserCreate` 不会进数据库，`User` 才会。
5. **业务码和 HTTP 状态是两个数。** 成功时 HTTP 200 且 `code` 为 0。记录不存在时 HTTP 404 且 `code` 为 10000。
6. **改表结构不会自动迁移。** 当前只有 `create_all`。
7. **`/health` 的 JSON 和业务接口不一样**，它没有 `code` / `data` 外壳。
