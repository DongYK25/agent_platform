# RAG 学习流程

## 阶段 1：先做一个最简单的 RAG

你应该重点研究以下问题：

1. 用户问题是如何转换成向量的？
2. PostgreSQL 是如何计算向量相似度的？
3. 为什么设置 `k=3` 就可以返回三个结果？
4. 相似度分数到底代表什么？
5. 能否限制只搜索某个知识库的文档？

## 阶段 2：研究 Chunking，也就是如何切分文档

先研究 Chunking。

你可以自己准备一份 1000 字左右的公司制度文档，然后用三种方式切分：

| 切分方式 | 实验设置 |
| --- | --- |
| 固定长度 | 每个 Chunk 500 Token |
| 固定长度 + 重叠 | 500 Token，Overlap 100 |
| 按段落切分 | 尽量保留完整段落 |

然后使用相同的 Embedding 模型、相同的问题集进行检索。

观察结果：

- 哪种切分方式更容易找到正确答案？
- Chunk 太大有什么问题？
- Chunk 太小有什么问题？
- 上下文被切断后会发生什么？
- Overlap 是否真的有帮助？

> 这里不要只看相似度分数，而要看实际返回的文本是否包含回答问题需要的信息。

我认为这是 RAG 学习中最值得花时间的部分之一。

## 阶段 3：学习 Hybrid Search 混合检索

完成前两个阶段，你就已经有了一个基础 RAG。

接下来尝试一个实际问题。

假设知识库里面有一条：

```text
产品型号：XH-2026-A
设备最大工作温度：85℃
```

用户问：

```text
XH-2026-A 的最大工作温度是多少？
```

向量检索能够找到它。

但是有时用户查询产品型号、订单编号、员工编号、特殊专业术语时，关键词匹配可能比语义匹配更可靠。

这就引出了 Hybrid Search：

- **Vector Search**：语义检索。
- **Keyword Search**：关键词检索。
- **Hybrid Search**：把两种检索结果结合。

你可以先研究 PostgreSQL 的全文检索，再研究如何与 pgvector 组合。

## 阶段 4：学习 Reranker

这个阶段再引入 Reranker。

假设检索出来了 10 个 Chunk。

它们的向量相似度排名可能是：

```text
Chunk A：0.91
Chunk B：0.89
Chunk C：0.86
Chunk D：0.84
...
```

但向量相似度高，并不意味着它一定能回答用户的问题。

Reranker 可以进一步分析：

> 用户的问题和这段文本到底有多相关？

先通过向量检索召回候选内容，再使用 Reranker 重新排序，最后取排名靠前的几个 Chunk 给 LLM。

这个阶段你需要理解 Bi-Encoder 和 Cross-Encoder 的基本区别。
